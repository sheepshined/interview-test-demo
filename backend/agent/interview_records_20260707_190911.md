## 第1题

**题目**: Django ORM 中 select_related 和 prefetch_related 的区别？

**你的回答**:

elect_related 解决的是 正向一对一和正向一对多 的查询，它通过JOIN把关联表的数据一次性查出来，只产生 1条SQL。比如订单查用户，用这个就很合适。  prefetch_related 解决的是 多对多和反向一对多 的查询，它会先查主表，再根据主表ID批量查关联表，产生 2条SQL，然后在内存里组装。比如用户查订单列表，或者文章查标签，就用这个。  实际项目中我的选择标准是：  如果关联对象是 唯一且必有的（比如商品→品牌），我肯定用 select_related，因为JOIN效率最高。  如果关联对象是 多个的（比如作者→多本书），我会用 prefetch_related，避免JOIN导致主表数据重复膨胀。

**标准答案**: select_related 使用 SQL JOIN 一次性获取关联数据，适用于外键（ForeignKey）和一对一（OneToOne）关系。prefetch_related 使用额外的查询并 Python 层面连接，适用于多对多（ManyToMany）和反向外键。前者减少 SQL 查询次数但造成大表 JOIN，后者执行多条查询但各自简单。

## 第2题

**题目**: 数据库索引的原理？什么时候索引会失效？

**你的回答**:

索引本质上是一种排好序的数据结构，在MySQL InnoDB里默认是B+树。  它的核心作用是减少扫描的数据页数。没有索引时，查询得从头到尾遍历整张表（全表扫描）；有了索引，B+树可以从根节点快速定位到叶子节点，叶子节点上挂着主键ID，再通过ID回表查完整行数据。  覆盖索引的话，叶子节点直接存了要查的字段，连回表都省了，这是我最常用的优化手段。

**标准答案**: 索引本质是 B+Tree 数据结构，通过有序存储加速查找。索引失效场景：1) WHERE 条件对索引列做函数运算 (WHERE YEAR(col)=2024) 2) 前导模糊查询 (LIKE '%abc') 3) 联合索引未遵循最左前缀匹配 4) 类型隐式转换 (WHERE varchar_col=123) 5) OR 条件中部分列无索引。Python 中对应：用 Django ORM 的 explain() 查看执行计划，确保索引命中。

## 第3题

**题目**: FastAPI 和 Flask 的核心区别？高性能的原因是什么？

**你的回答**:

Flask是同步微框架，基于WSGI协议（也就是PEP 3333）。它的核心设计哲学是"简洁灵活"，只提供最基础的请求响应和路由功能，其他像ORM、表单验证都要靠扩展生态来补。它的请求处理是同步阻塞的，每个请求在视图函数执行完之前会一直占用工作线程。  FastAPI是异步框架，基于ASGI协议，同时兼容WSGI。它的设计思路是"现代化全栈"，把类型提示、自动生成OpenAPI文档、数据校验这些功能直接内嵌在框架里，基本不需要额外集成第三方库。  FastAPI高性能的主要原因：  我认为有三层：  第一层：异步IO和事件循环 这是最根本的。FastAPI基于Starlette，底层是asyncio。对于I/O密集型操作（比如调外部API、读写数据库、文件操作），用async/await可以让单线程在等待IO时切换处理其他请求，而不是像Flask那样干等着。虽然Python的GIL存在，但在网络IO场景下，异步确实能大幅提升并发能力。  第二层：Pydantic的数据校验效率 FastAPI的请求参数解析和验证用的是Pydantic，它底层大量使用__slots__和C扩展（pydantic-core是Rust写的），验证性能远高于Flask + marshmallow或WTForms的组合。  第三层：ASGI协议本身 ASGI支持WebSocket、HTTP/2长连接这些WSGI处理不了的长连接场景，同时在请求生命周期管理上更高效，能复用连接，减少握手开销。

**标准答案**: FastAPI 支持异步原生、自动 OpenAPI 文档、Pydantic 数据验证、基于 Starlette 和 Uvicorn 高性能。Flask 是同步模型、WSGI + 插件生态成熟。FastAPI 高性能原因：1) 异步非阻塞 2) Starlette 底层 3) Uvicorn ASGI 服务器 4) Pydantic 高效序列化。选 FastAPI 用于 API 服务/微服务/高并发。

## 第4题

**题目**: Python 中深拷贝和浅拷贝的区别？

**你的回答**:

好的面试官，关于深拷贝和浅拷贝，我直接用实际场景来说。浅拷贝本质上只复制了最外层的容器，里面的子对象还是指向原来那一份，所以当你修改嵌套结构里的内容时，原对象会跟着变，这个坑我在处理嵌套列表和ORM对象缓存时都碰到过。比如有一次我把用户对象浅拷贝后放到缓存里，结果业务逻辑改了缓存里的地址列表，数据库里的用户地址也跟着改了，这种隐式共享很容易引发诡异的Bug。深拷贝则是从头到尾递归复制出一份完全独立的新对象，修改哪一层都不会影响原对象，代价是性能和内存开销更大，尤其遇到循环引用时还得额外处理。我的原则是，如果对象结构简单且只读，浅拷贝没问题；但只要涉及嵌套可变对象或者后续有修改操作，我会优先用deepcopy保证隔离性，宁可牺牲一点性能也不留隐患。以上是我在这块的经验总结。

**标准答案**: 浅拷贝 `copy.copy()` 只复制对象的第一层，内部的嵌套对象仍是引用同一内存。深拷贝 `copy.deepcopy()` 递归复制所有层级的对象，完全独立。对于不可变对象，深浅拷贝行为相同。
